## User-friendly free product

Implement `/calculators`, `/calculators/[slug]` and `/pricing` with original forest-green/ivory/lime Joff design. The hub uses search over common terms as well as tax names, task-based categories, clear descriptions and related-tool links. Categories: salary/pay, retirement, investments/assets, business/property, deductions/benefits, deadlines/documents. Accurate counts distinguish working calculators, working guides and pending research; a unavailable formula card cannot look enabled.

Each tool follows one consistent sequence: explain what it answers, ask a short grouped form with visible labels/context help, show result plus breakdown/assumptions, and give a concrete next step. Users select assessment year or transaction date where applicable. A non-year-dependent conversion/projection explicitly says so. New tools default to blank values, never fabricated personal data; "Try an example" is deliberate and labelled fictional. Preserve in-form inputs on validation failure. Inputs are not silently rounded or coerced. Unknown legal classification produces guidance and a named blocker. The coverage audit also tracks known **submodes**, because 33 category names do not establish full functional parity (notably UIF benefits, retirement tax-saving/growth, hourly gross/net, retrenchment ordinary/severance and payroll single/multiple employees).

Genuinely working free extras:

- Session scenario comparison of up to three compatible cases with named differences, amounts, assumptions and rules/year provenance. Require the same tool/output schema or an explicit semantic compatibility key; a common `resultKind` alone is insufficient. Cross-year comparison is explicit. Do not compare unrelated deduction components as if all were annual tax liability.
- Real text/JSON download, readable print and copy-summary containing inputs, calculation, scope, sources and timestamp. No personal values in share/query URLs; no fake PDF button.
- Related actions such as bonus to annual-tax comparison, interest to investment context, deduction schedule to preparation checklist, and retirement saving to TFSA context. Do not sum independent components without a reviewed combined engine.
- Non-sensitive favourite tool slugs may persist as preferences; monetary scenarios/comparisons remain session-only and labelled accordingly. Existing owner-scoped D1 preparation save/load stays free and unchanged. Tool results can link to preparation, but do not silently overwrite an existing draft or claim a new calculator result validates the return.
- Deadline `.ics` downloads only for confirmed operational dates and category, with source and timezone. A derived 26 February 2027 provisional payment date remains separately labelled and is excluded from calendar export until the guide contract's operational notice check is satisfied. A real local file for voluntary import is not an active reminder service.
- Document/refund guides remain useful when a numeric case is unsupported. Official next steps and deliberate links to SARS are available without a paywall.

The hosted release remains private with its existing sign-in gate. Do not advertise "no login" while private access requires identity. Calculator use itself needs no new signup, payment or storage of financial input. Future public anonymous availability is separate from current access policy.

## Honest free-to-paid journey

Keep all live calculators, explanations, comparisons, exports and existing preparation functionality free. The pricing page presents a **proposed service preview**, not a purchasable or functioning premium product. It can show the intended difference between self-guided tools and accountable reviewed help, with a working route back to free preparation or a feedback capture only if actually implemented. No checkout, payment fields, fake entitlement, "unlock now", fake waitlist submission or claimed practitioner response.

Proposed paid outcome: a named registered practitioner's review of reconciled documents, unsupported-case resolution, a reviewed action plan/handover, and scoped assistance responding to SARS correspondence. These services require contracted registered people, defined capacity, consent, secure documents, support/refund terms, operating entity and legal/privacy review before sale. Actual filing needs separately authorised integration or a real practitioner workflow. Pricing remains a hypothesis, informed by competing guided filing at R215/R565/R895 and expert filing from R1,299; do not imply unreviewed preparation software offers the same service. Test willingness to pay for the reviewed outcome, not an artificial calculator/export restriction.

Return reasons now: useful related tools, favourite shortcuts, saved free preparation, tax-year/date changes and a downloadable published deadline calendar. Year-round premium monitoring or reminders are future capabilities until implemented and operationally validated.

## Engineering and ownership

The catalog is the single coverage registry. Every entry declares slug/title/category, task synonyms, status, input/output schema, result kind, year/date policy, source contract/rules version, assumptions/exclusions, examples, related tools and export labels. Status is derived from implemented approved evaluator coverage, not a manually inflated UI count. Engines return a typed supported result or named blockers; their output declares whether it is annual liability, incremental/component tax, deduction, schedule, projection or guide. The UI never fabricates missing results or treats a component as an assessment.

The agreed engine boundary is `evaluateCalculator(id, assessmentYear, Record<string,string>)`, returning `status: supported|blocked|invalid`, labelled formatted `items`, `blockers`, `assumptions`, `provenance`, optional `steps` and `fieldErrors`. Add explicit `resultKind` for comparison compatibility and interpretation. `supported` for a checker/tracker means a useful guide within its contract, not an official filing/status determination. `CALCULATORS` declares `id`, category/title/description, mode `estimate|checker|tracker`, year policy, scope summary, fields with types/options/help/bounds/sections, labelled example and contract availability. No registry entry is live unless its approved evaluator or branching guide exists; counts derive from that availability. Transaction-date specialists declare their applicable rule periods rather than relying on the income assessment-year selector alone.

Proposed split agreed with parent: **coder owns frontend** routes/components/style/hub and shared result/comparison/export UX; **verification agent owns registry, pure evaluator modules, exact schemas, fixtures and engine tests** under new `lib/calculators/` and calculator test files. Existing calculation/model/repository/auth files are untouched unless an explicit integration need is reviewed. Root owns integration/build/deployment and source publication. Agree the shared registry/result TypeScript contract before parallel edits; each agent has separate files and communicates contract changes. No extra dependency or database migration is necessary for session-only tools.

Use existing reviewed salary engine for supported salary cases; do not weaken its screening to accept unrelated calculator inputs. Tax tables are year-versioned. Specialists with financial-year or transaction-date regimes get distinct explicit configuration. Pure input schemas enforce finite bounded values, enum/classification unknowns and date validity. If any server persistence/export is introduced, existing authoritative identity/owner scoping/same-origin/no-store/strict body limits apply without exception.
